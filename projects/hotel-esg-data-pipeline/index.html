Hotel utility data pipeline and ESG reporting

Forty hotels type their monthly electricity, water and gas figures into a portal by hand. Before anyone can report a carbon footprint, those numbers have to match the bills. I built a pipeline that checks every value, fixes what it can prove, flags what it can't, and records every change.

The data is simulated because real hotel utility data is confidential. That has an upside: I injected realistic errors on purpose and kept an answer key hidden from the pipeline, so its accuracy is measured, not claimed.

The problem

Sustainability reports roll up hundreds of monthly utility figures. Each one is typed by a hotel engineer, and each mistake flows straight into the reported emissions.

The errors are mundane but costly: MWh entered as kWh (a 1,000× understatement), decimals shifted, months missing or submitted twice, property IDs typed three different ways, and figures that simply don't match the bill.

On top of that, some providers bill 15th to 14th, so a bill never lines up with a calendar month. Naive pro-rating blurs month-to-month changes and raises false alarms.

How the pipeline works

Each stage writes to two logs: issue_log.csv (what was found, by which rule, what was done) and change_log.csv (old value, new value, reason, source). Any number in the final report can be traced back to its origin.

  1. Standardise

    Repair IDs (htl-001, HTL001 → HTL-001), unify period formats, convert MWh and litres to base units.

  2. De-duplicate

    Drop exact duplicates; for conflicting ones keep the value closest to the bill.

  3. Build reference values

    Pro-rate calendar bills. For offset billing cycles, infer each month from both bills that touch it and flag it only when every inference disagrees.

  4. Reconcile and classify

    ±2% tolerance vs the bill. Ratio ≈ 0.001 means a unit mislabel, ≈ 10× a decimal shift, anything else a transcription mismatch.

  5. Fill gaps

    Compare expected vs received records. Fill from the bill, or estimate from median intensity × room nights and mark it estimated.

  6. Check plausibility

    Robust z-score (median / MAD) on consumption per occupied room night. Outliers the bill confirms are kept and escalated.

  7. Chase missing invoices

    List every expected bill that never arrived.

  8. Calculate emissions

    Scope 2 from electricity × grid factor, Scope 1 from natural gas, plus intensity per occupied room night.

    What this means for a data team

    • Fix with proof, flag without it

      Values are only overwritten when a bill proves the right number. Everything else is flagged for a person to decide.

    • Audit-ready by default

      The change log answers "why is this number different from what the hotel sent?" in one lookup.

    • Follow-up lists, not just dashboards

      The invoice gap report and the list of properties to chase turn data checks into the team's daily work queue.

    • Rules you can explain

      Every check is a readable rule with a tolerance, so clients and auditors can agree on it before the numbers are reported.
